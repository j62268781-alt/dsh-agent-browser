## #1 `webform-fine` step7「Submit the form」→「页面上没有可操作的元素」（假阴性）

**现象**：r3 全量里 `webform-fine` 第 7 步 `no_progress` / `页面上没有可操作的元素`（rounds=1），
但前 6 步都 `needs_verification`/`likely_done`。该步 `truth=false`。

**复现命令**（真跑本插件的循环，带决策 trace，输出在 docs/probes 内）：

```bash
node bench/run.mjs --tier base --only webform-fine --session dsh-probe --trace --verbose \
  --out docs/probes/r8-webform-trace.json
# → ✗ webform-fine  no_progress  truth=false 7/7 steps · 19 calls · 20.1s
```

**原始证据 1：step7 的实际动作序列**（`docs/probes/r8-webform-trace.json`，step7 trace）：

```
第 1 步：页面内抽取 17 个元素（跳过被遮挡 1 个）→ 20 个候选
第 1 步：点击「Submit」（button，附近: Dropdown (select) ...） ✓
第 2 步：页面内抽取没有可用元素（0 个元素）→ 退回整树观察
第 2 步：点击后页面在跳转 → 事件驱动等待到变化再观察
第 2 步：页面内抽取没有可用元素（0 个元素）→ 退回整树观察
第 2 步：页面上没有可操作的元素（独立确认 p=0.99，不作为完成依据）→ 停
```

**原始证据 2：提交后的目标页确实没有任何可交互元素**（不是抽取器漏抽）：

```bash
agent-browser --session dsh-probe open 'https://www.selenium.dev/selenium/web/submitted-form.html?my-text=Jev&my-password=pw123&my-textarea=hello+world&my-select=2&my-radio=on&my-date='
agent-browser --session dsh-probe eval '...selector 命中数...'
# → {"selectorMatches":0,"allElements":17,"bodyText":"Form submitted\n\nReceived!","title":"Web form - target page"}
```

- EXTRACT_SCRIPT 在该页返回：`items=0`、`text="Form submitted\n\nReceived!"`、`truncated=false`；
- `snapshot -i` 也只有一个 heading：`- heading "Form submitted" [level=1, ref=e1]`；
- 截图：`docs/probes/r8-webform-submitted.png`。

**原始证据 3：断言还有第二个坑——第 5 步填的日期被第 6 步点 radio 清空**
（页面在 `[name=my-date]` 上挂了 bootstrap-datepicker 1.9.0）：

```bash
agent-browser --session dsh-probe open https://www.selenium.dev/selenium/web/web-form.html
agent-browser --session dsh-probe fill '[name=my-date]' '09/16/2026'
agent-browser --session dsh-probe eval "document.querySelector('[name=my-date]').value"   # → "09/16/2026"
agent-browser --session dsh-probe check '#my-radio-2'
agent-browser --session dsh-probe eval "document.querySelector('[name=my-date]').value"   # → ""
```

页面脚本（实测）：`$('[name=my-date]').datepicker({})`。复现 3/3 次：
`fill date=09/16/2026` 后 `check '#my-radio-2'`，date 值立刻变回 `""`。
提交后的 URL：`...&my-radio=on&my-date=&...` → 任务断言要求 `q.get('my-date')==='09/16/2026'`，**即使提交成功也必然 false**。

**归因**：
1. **工具能力（循环终态规则）— 高置信**：抽取结果正确（0 items 是页面真实状态）。
   缺的是「0 候选时的收尾」：页面已经跳转、正文是 `Form submitted / Received!`，循环却以
   `no_progress` 收场（不计完成）→ **假阴性**。同一根因也解释了 `new-window` 的
   `no_progress / 页面上没有可操作的元素`（r3 里该步 `truth=true`，也是假阴性）。
2. **站点/任务交互 — 高置信**：bootstrap-datepicker 在 radio 点击（blur）时清空输入框，
   任务断言依赖该值 → 这是页面第三方组件的真实行为，抽取/点击都没错。

**建议修法**：
- 抽出终态逻辑：`items.length === 0` 且页面有变化（URL/title/text 变化或 async 跳转中）时，
  不要直接 `no_progress`；把 `text`+`title`+`url` 交给同一个 goal_done 判定，
  满足即返回 `needs_verification`（附「页面无可操作元素，已按文本确认」reason）。
- 顺带收益：`new-window`（`no_progress`+`truth=true`）会被同一修复救回。
- 日期被清空属于第三方组件行为：可在「提交/收尾前」对调用方给过的值做一次 readback 校验
  （失配则重填），否则 `webform-fine` 的断言永远 false。

**置信度**：终态缺陷 0.9（trace + DOM 双证）；日期清空 0.9（3/3 复现 + 提交 URL 里的 `my-date=`）。

## #7（Lead 加急，红线）`wiki-search` 假完成：搜索建议**抽得到**，判断层选了陷阱项

**现象**：r3 全量里 `wiki-search` `needs_verification` / `goal_done=0.96，确认 p=0.92`，但 `truth=false`
（假完成）。r8 复跑同一条任务 3 次全部 `error`（batch 退出码 1 / open 超时）。

**复现命令**：

```bash
# 建议下拉在 EXTRACT_SCRIPT 眼里的可见性（输入 Alan Turing 后 0/150/400/800ms）
node scripts/probes/wiki-search-probe.mjs

node bench/run.mjs --tier base --only wiki-search --session dsh-probe --trace --verbose \
  --out docs/probes/r8-wiki-search-trace4.json
```

**原始证据 1：建议项在候选池里（不是抽取漏项）** — `docs/probes/r8-wiki-search-suggest.txt`

| 采样 | items | covered | 名称含 "Alan Turing" 的候选 | 目标条目 | 陷阱 Enigma | 可见 listbox |
|---|---|---|---|---|---|---|
| t≈5ms | 267 | 2 | 0 | ✗ | ✗ | 0 |
| t≈155ms | 279 | 15 | 11 | ✓ | ✓ | 1 |
| t≈419ms | 279 | 15 | 11 | ✓ | ✓ | 1 |
| t≈806ms | 279 | 15 | 11 | ✓ | ✓ | 1 |

候选池里同时有（同一份 extract）：

```
3 | a | "Alan Turing English computer scientist (1912–1954)"     ← 目标条目
6 | a | "Alan Turing: The Enigma Biography by Andrew Hodges"     ← 陷阱（传记书）
13 | a | "Search for pages containing Alan Turing"               ← 陷阱（搜索页）
```

DOM 结构：建议容器是 `UL.cdx-menu__listbox[role=listbox]`，条目是 `LI[role=option]`
（`el.matches(抽取 selector) === false`，因为 **selector 里没有 `[role="option"]`**）；
但每个 LI 内部有 `<a>`，被 selector 命中，所以**以 `role=a` 进了候选**——
抽取结果是"能用"，只是依赖内层 `<a>` 这一层。

**原始证据 2：两个陷阱各自的落点（实测 click）**

```bash
agent-browser --session dsh-probe fill 'input[name=search]' 'Alan Turing'
# 点 "Alan Turing: The Enigma" 建议 →
#   https://en.wikipedia.org/wiki/Alan_Turing:_The_Enigma        ← assert 要求 pathname === '/wiki/Alan_Turing'，必 false
# 点 "Search for pages containing Alan Turing" 建议 →
#   https://en.wikipedia.org/w/index.php?title=Special%3ASearch&fulltext=1&search=Alan+Turing
```

而 r8 复跑的 `record.error` 里，失败 batch 的 `snapshot.origin` **正是**
`.../w/index.php?title=Special%3ASearch&fulltext=1&search=Alan+Turing`
（见 `docs/probes/r8-wiki-search-trace2.json` 的 `record.error`）——
即本次 run 判断层点的就是「Search for pages containing Alan Turing」这个陷阱。
r3 的假完成则更可能是落在 Enigma 页（标题/正文都含 "Alan Turing" → judge 误认完成）。

**原始证据 3：Enter 才是确定性正确动作；另有独立 Search 按钮**

```bash
# 填完立即按 Enter（建议下拉还没出来）→ /wiki/Alan_Turing ✓
# 填完等 1s（建议下拉已开）再按 Enter → /wiki/Alan_Turing ✓
agent-browser --session dsh-probe fill 'input[name=search]' 'Alan Turing'
agent-browser --session dsh-probe press Enter
```

独立 Search 按钮存在：`<button class="cdx-button cdx-search-input__end-button">Search</button>`
（无 `type` 属性，在 `#searchform` 里；extract 里是 `role=button, name="Search"`）。
点它 + 已输入也到 `/wiki/Alan_Turing`（实测），所以按钮本身不是陷阱，**建议链接才是**。

**归因**：
1. **判断层选错（不是抽取缺陷）— 高置信**：11 个候选的名字都以 "Alan Turing" 开头，
   目标条目（idx3）与陷阱（idx6/idx13）名字高度相似；judge 选了陷阱链接。
2. **跳转后观察/标签页状态不稳 — 待定（低置信）**：复跑 3 次都 `error`（`batch 退出码 1`），
   错误里 `snapshot.origin` 是陷阱页或**旧标签页**（`Confectionery_store&action=edit`）、`refs:{}`；
   bench 把错误截到 500 字符，看不到具体失败的子命令 → 无法定位是哪个 batch 子命令失败。
   这是工具/会话层问题，不是网络（同页直接 `batch` 实测 exit=0）。
3. **抽取可加固（低优先）**：selector 缺 `[role="option"]`，目前靠 LI 内层 `<a>` 兜住。

**建议修法**：
- 填完 searchbox 且 goal 含 search/open 时，把「按 Enter」当**确定性**动作优先执行
  （现有 `control:press_enter` 只在「刚填过输入框」时提供；这里正好命中，但判断层没选它）。
- 判断层提示词加规则：目标点名条目时选**名称与目标完全一致**的候选；带副标题/解释/
  "Search for pages containing…" 的不是目标页；落在 `Special:Search` 结果页不算完成。
- `bench/run.mjs` 的 error 记录别截断到 500 字符（保留 batch 逐条结果），否则工具侧失败无法归因。

**置信度**：抽取无缺陷（建议项确实进候选）0.95；判断层选错 0.85；`error` 的具体子命令 0.4（待定）。

## #8（Lead 加急）`infinite-scroll` 任务口径：一次滚动只加载 **1** 段，assert 要 3 段

**现象**：r3 `infinite-scroll` `likely_done` / `goal_done=0.77，确认 p=0.67`，`truth=false`。

**复现命令**：

```bash
agent-browser --session dsh-probe open https://the-internet.herokuapp.com/infinite_scroll
# 每次滚动 1000px，等 1.5s，数 .jscroll-added
agent-browser --session dsh-probe scroll down 1000
agent-browser --session dsh-probe eval "document.querySelectorAll('.jscroll-added').length"
```

**原始证据（可重复）**：

| 状态 | `.jscroll-added` | scrollHeight | 正文新增信号 |
|---|---|---|---|
| 初始 | **1** | 691 | — |
| 滚动 1 次后 | **2** | 1107 | 只有新段落文本，无 "loaded N" |
| 滚动 2 次后 | **3** | 1507 | 同上 |
| 滚动 3 次后 | **4** | 1923 | 同上 |

- 一次滚动**恰好** +1 段；起始就有 1 段。
- 页面正文没有"已加载 N 段"这类可读计数（`hasLoadingText=false`，正文尾部只有段落 +
  `Powered by Elemental Selenium and Sauce Labs`）。截图：`docs/probes/r8-infinite-scroll-after3.png`。

**归因**：**任务定义（口径不一致）— 高置信**。goal 是 "Scroll down to load more paragraphs"
（一次滚动就会加载），assert 却是 `length >= 3`（=起始 1 + 至少滚 2 次）。
滚一次后 judge 认为"确实加载了新段落"（likely_done）完全合理，但断言必 false。
不是抽取/点击缺陷，也不是网络。

**建议修法**（bench 侧，不涉及 src）：
- goal 改成 "Scroll down until at least 3 paragraphs have loaded"（明确可验证条件），或
- assert 改成 `length >= 2`（与"滚动一次"口径一致）。
- 若要在产品侧兜：对"滚动加载"类目标，goal 里必须带可验证条件，循环才能知道该滚几次。

**置信度**：0.9（计数确定、可重复，且与 r3 的 likely_done 完全吻合）。

## #3 `ti-sort-table`：列**真的可排序**，但表头没进候选池（抽取缺陷）

**现象**：r3 `ti-sort-table` `budget` / `达到最大步数 10` / rounds=6，`truth=false`；
r8 复跑：`ambiguous` / `置信 0.07、前两名差 0.02` / 22 个候选 / rounds=1。

**复现命令**：

```bash
node bench/run.mjs --tier base --only ti-sort-table --session dsh-probe --trace --verbose \
  --out docs/probes/r8-ti-sort-table-trace.json
node scripts/probes/extract-probe.mjs --url https://the-internet.herokuapp.com/tables --top 60
```

**原始证据 1：页面确实实现了排序（jQuery tablesorter）**

```
页面脚本：.../jquery.tablesorter.min.js
内联：$(function(){ $("#table1").tablesorter(); $("#table2").tablesorter(); });
<th class="header"><span>Last Name</span></th>   ← tablesorter 已挂 class=header
```

**原始证据 2：点表头排序真的生效**

```bash
agent-browser --session dsh-probe click '#table1 thead th:nth-child(1)'   # Last Name
# 之后首列顺序：Bach, Conway, Doe, Smith   ← assert 要的 'Bach' 就在首位
# 表头 class 变为：header headerSortDown
```

**原始证据 3：extract 里没有表头候选**

```
{"items":18,"covered":0,"truncated":false,...}
0..17 全是 edit/delete 链接，没有任何 "Last Name" / th / header 候选
```

trace 也直接印证：`页面内抽取 18 个元素 → 22 个候选`，
`goal_done=0.53 stuck=0.07 候选=22 置信=0.07` → `判断层分不清 → ambiguous`。
22 个候选里没有可达排序的动作，judge 只能"分不清"。

**归因**：**候选抽取缺陷 — 高置信（0.95）**。`EXTRACT_SCRIPT` 的 selector 是
`a,button,input,select,textarea,summary,label[for],role=…,[onclick],[tabindex]` 等，
**不含 `th` / `[role="columnheader"]`**。该页的 `th.header` 没有 onclick 属性、
没有 role/tabindex，tablesorter 是用 jQuery 事件委托绑的 → 抽取阶段直接漏掉。
不是任务问题（页真能排），也不是判断层问题（它根本没见过这个动作）。

**建议修法**：把可点击表头纳入抽取——
`th`（有 `[role=columnheader]`、`class` 含 `sort`/`header`、或 `getComputedStyle(th).cursor === 'pointer'` 时），
role 映射成 `columnheader`，`near` 仍给所在行文本。
注意只加"看起来可点"的 th（否则稠密表格页会多出几十个噪声候选）；本页加完 18→24，无压力。

**置信度**：0.95（DOM/脚本/点击/extract/trace 五重证据）。

**13:37 并行修复后复验**：新 `lib/extract.js` 已含 sortable header 抽取，
同一页面 extract 从 18 → **30 items**，多出 6 个 `columnheader`（含 `"Last Name"`，两个表各 6 个）：

```
18 | columnheader | "Last Name" | 0
19 | columnheader | "First Name" | 0
…
```

即「表头不在候选」这一条已被该改动修掉；建议 lead 的最终 diff 里保留这段并补一个断言级回归
（点 columnheader「Last Name」→ `#table1 tbody tr td` 首格 === 'Bach'）。

## #4 `react-select`：`input[role=combobox]` 的 role 被抽取器覆盖成本 textbox → 相关性门退回整树 → 判断层点了「Remove Purple」干扰项

**现象**：r3 `react-select` `ambiguous` / `置信 0.44、前两名差 0.09`，`truth=false`；
r8 复跑（`docs/probes/r8-react-select-trace2.json`）`ambiguous` / `置信 0.11、差 0.00` / 2 rounds。

**复现命令**：

```bash
node bench/run.mjs --tier hard --only react-select --session dsh-probe --trace --verbose \
  --out docs/probes/r8-react-select-trace2.json
node scripts/probes/extract-probe.mjs --url https://react-select.com/home --top 100
```

**原始证据 1：抽取器把 `role=combobox` 覆盖成 `textbox`（代码级）**

`src/extract.ts` 的角色推导是：

```js
let role = el.getAttribute('role') || tag            // 先取显式 role
if (tag === 'input') role = type === 'checkbox' ? … : 'textbox'   // ← 无条件覆盖
```

react-select 的输入框是 `<input role="combobox" tabindex="0" aria-expanded="false" …>`，
于是抽取结果里是 **10 个 `role=textbox` 且 name="" 的匿名候选**（实测 `25|textbox|""`、`35|textbox|""`…），
**一个 `combobox` 都没有**。

**原始证据 2：相关性门因此退回整树，把「Remove Purple」带进候选**

trace（r8 复跑）：

```
第 1 步：抽取结果里没有与目标相关的候选（目标词 the/first/dropdown/page，缺角色 combobox/option）→ 退回整树观察
```

- `src/extract.ts`：**显式 role 优先**——`const explicit = el.getAttribute('role'); let role = explicit || tag;`

- 判断层提示词加一条：「Remove X / 删除已选」不是选择动作；"choose the colour X" 应先打开
  combobox 再点同名 option。

**置信度**：role 覆盖缺陷 0.95（代码+DOM+trace 三重）；judge 被 Remove Purple 误导 0.99（trace 直证）；
